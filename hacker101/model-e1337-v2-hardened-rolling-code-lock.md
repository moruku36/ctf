# Model E1337 v2 - Hardened Rolling Code Lock

## 結果

2026-11-01 にフラグを提出し、Hacker101 CTF の一覧で **1/1**、合計 **172 点**を確認した。インスタンス固有の URL、表示コード、フラグは掲載しない。

## 観察

画面には数値コードの入力欄と `Unlock` ボタンだけがある。誤った数値を `POST /unlock` の `code` に送ると、応答は `Code incorrect. Expected <number>` と、今回必要だったコードを示す。しかし次の送信時にはコードが変わるため、表示値をそのまま再送しても解除できない。

同じインスタンスの `GET /rng` で乱数生成処理のソースを読めた。`setup(seed)` は64ビットの seed を受け取るが、16回のループで各回2ビットずつ消費するため、実際に状態に反映されるのは下位32ビットである。`next(64)` は64ビットの出力を返し、出力ビットごとに64ビット状態を3回更新する。

## 解法

この生成器のビット演算は、GF(2) 上のアフィン変換として扱える。まず seed が0の出力を基準にし、32個の各1ビット seed の出力との差分を計算する。この32個の差分から、観測した64ビット出力と seed の関係を64本の線形方程式にする。GF(2) のガウス消去で有効な32ビット seed を復元する。

最初に誤ったコードを1回送り、表示された出力を記録する。[計算スクリプト](model-e1337-v2-solver.py)にその値を渡す。今回は追加で2回目の誤入力から得た表示値を渡し、予測した2つ目の出力と一致することを確かめた。スクリプトが算出した3つ目のコードを入力すると解除に成功し、フラグが表示された。フラグを提出して 1/1 を確認した。

```text
python model-e1337-v2-solver.py <最初の表示コード> <2回目の表示コード>
```

実行中に別の要求が生成器を進めた場合、予測する出力の順番が変わる。2回目の照合が不一致なら、そのまま送信せず、観測値と送信順を確認する。

## 学んだ点

出力をそのまま再送できない仕組みでも、生成器の状態が小さな seed から決まり、出力との関係が線形なら、少数の観測から次の値を予測できる。seed の見かけのビット幅ではなく、`setup` が実際に使うビット数を調べることが重要だった。
