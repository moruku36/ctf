# Encrypted Pastebin — 解法記録

- 実施日: 2026-10-30
- 対象: [Hacker101 CTF の Encrypted Pastebin](https://ctf.hacker101.com/ctf)
- 状態: **4/4 提出済み**、CTF 一覧で全体 115 点を確認
- 演習インスタンスのホスト名、暗号化された個別リンク、フラグ値は公開しない

## 初期確認

タイトルと本文を投稿すると、`?post=...` を持つ長い共有 URL へ移動した。ページには投稿内容が表示される。公式ヒントは暗号化リンクに注目する内容だった。

エラー画面から、`post` は Base64 の `+` を `-`、`/` を `!`、`=` を `~` に置き換えた形式と分かった。復号処理は AES-CBC を使い、先頭16バイトが IV。自分の短い投稿のリンクは Base64 を戻すと160バイトだった。

## 受理されたフラグ 1: 不正なリンクと詳細エラー

`/?post=1` を開くと、パディングの誤りを含む詳細なトレースバックとフラグが表示された。フラグを提出し、受理を確認した。復号に失敗した理由を画面へ詳しく出していることが、後の検証の手がかりになった。

## 受理されたフラグ 2: CBC のブロック操作で別の投稿を参照

公開解説を手掛かりに、リンクの復号後が概ね次の JSON になることを確認した。

```json
{"flag":"<演習用の値>","id":"<投稿ID>","key":"<投稿用の鍵>"}
```

実際のシリアライズにはキーの間に空白が入る。フラグが64桁の16進値なので、6番目の平文ブロックは `$FLAG$\", \"id\": \"` と分かる。このブロックの直前の暗号文と既知の平文を XOR して中間値を求め、新しい IV に `{\"id\":\"1\", \"i\":\"` が現れるようにした。先頭5ブロックを捨て、残りの暗号文はそのまま使った。

これで投稿 ID 1 のタイトルが復号エラーに表示され、別のフラグを確認して提出した。本文の鍵は自分の投稿のものなので本文の復号には失敗した。

## 受理されたフラグ 3: パディングオラクルでリンクの値を復元

エラーの `PaddingException` の有無を使い、自分のリンクの暗号文を16バイトずつ復元した。フラグ部分は64桁の16進文字列と分かっていたため、未知の各バイトの候補を `0123456789abcdef` の16種類に絞った。4ブロック・計1024回の検証でフラグ部分を得て提出した。CTF 一覧で **3/4** を確認した。

## 受理されたフラグ 4: 暗号化リンクを作り、追跡ログから投稿を見つける

本文表示の前に、復号した JSON の `id` で投稿を検索する。詳細エラーから、この ID が SQL 文へ文字列として組み込まれていることを確認した。パディングオラクルを逆向きに使い、次の JSON を復号するリンクを作った。

```json
{"id":"0 UNION SELECT GROUP_CONCAT(headers),'' FROM tracking"}
```

末尾ブロックから順に、中間値 `D(C_i)` をパディングの成否で求め、直前の暗号文ブロックを `C_(i-1) = D(C_i) XOR P_i` として決める。最終ブロックには PKCS#7 パディングを付ける。この4ブロックのリンク生成には、対象の演習インスタンスへ約6100回の応答確認を行った。

細工した ID は投稿テーブルではなく `tracking` テーブルの `headers` をタイトル列として返す。エラー画面のタイトルにその内容が表示され、内部のアクセス記録の `Referer` から暗号化された別の投稿リンクを確認できた。そのリンクのホスト部分を現在の演習インスタンスに置き換えて開くと、投稿本文に最後のフラグが表示された。提出後、CTF 一覧で **4/4、全体115点** を確認した。
