# HackerOne / VDP 実践設計: 発見期限ではなく、時間枠で進める

作成日: 2026-11-08

## 結論

**最初は1プログラム・1機能・1種類の仮説に絞り、2週間で計12時間の試行を行う。成果は「脆弱性1件」ではなく「根拠付きで検証・撤退を判断できること」とする。** これは提案であり、実対象の検査開始や自動実行を指示するものではない。

VDPで初めて有効な脆弱性を見つけるまでの時間は、現時点では見積もれない。数時間で見つかることもあれば、数十時間以上費やしても有効な発見がないこともある。これらは可能なシナリオで、成功率や平均値ではない。AIやComputer Useがあっても、発見・受理・報奨金・CVEは保証できない。

## 1. 現在地から始める

このリポジトリには既に多数のHacker101解法がある。[Hacker101の記録](../hacker101/README.md)では、2026-11-02時点で283点、Micro-CMS v1/v2、認可・API・モバイル関連などの完了が記録されている。これはリポジトリの記録であり、今回アカウント画面で再確認した値ではない。

[旧ロードマップ](hackerone-learning-roadmap.md)の2026-10-29進捗を現在地と取り違えない。全CTFの完走をVDP着手条件にせず、次は「解説を参考に解く」から「正常動作と仕様を理解し、独立した根拠を示す」への移行を優先する。CTFの得点だけでは実対象への準備完了を判定しない。

### 過去記録から引き継ぐこと

- [全体の索引](../README.ja.md)にはWizのクラウド系、PumpkinShell、Pwned Labs、Prompt Airlines等の実績がある。入門を最初から繰り返すより、得意なWeb/API・クラウドの権限境界を候補にする。
- [RESULTS.md](../RESULTS.md)は、公開解説由来のフラグ受理と独立した再現を明確に区別している。実VDPでもこの区別を維持し、「提出できた」だけでは発見実績に数えない。
- [Hacker101の記録](../hacker101/README.md)には503、ブラウザの遮断、タイムアウトによる停止がある。探索時間とは別に環境復旧時間を計測し、同じ失敗を反復しない。
- [Rend Asunder](../hacker101/rend-asunder.md)は1/3提出済みで、残る2件の未検証部分を明示している。高度な課題を全部解き切るまでVDPの準備を待たず、未完了課題と実践試行を別枠で管理する。

### それぞれの位置付け

| 場所 | 目的 | 成果・注意点 |
| --- | --- | --- |
| Hacker101 CTF | 意図的に用意された課題で練習 | 再現手順と理解。実システムへの検査許可にはならない |
| Hacktivity | 公開された実例を読む | 仮説と報告品質を学ぶ。掲載例だけで発見確率を推定しない |
| 実VDP | 組織の定めた範囲で問題を報告 | 報告窓口とルールが中心。報奨を前提にしない |
| Bug Bounty | 条件に合う有効な発見への報奨制度 | 重複・対象外・影響不足などで報奨なしの場合がある |

Hacker101は公式の学習コース、Hacktivityはコミュニティ活動と報告の参照先である。VDPと報奨制度の違いも確認して使い分ける。[Hacker101](https://docs.hackerone.com/en/articles/8456935-hacker-101)、[Hacktivity](https://docs.hackerone.com/en/articles/8410358-hacktivity)、[VDP vs BBP](https://docs.hackerone.com/en/articles/8368965-vdp-vs-bbp)

## 2. 時間の見積もり方

下表は**今回のために設定する作業予算**であり、HackerOneの統計やモデル性能のベンチマークではない。実作業時間と、運営回答を待つカレンダー時間を分ける。

| 作業 | 初回の配分目安 | 終了条件 |
| --- | --- | --- |
| 候補選定・規約確認 | 1〜2時間 | 対象、許可、禁止事項を1枚に整理。曖昧なら実検査しない |
| 公開事例の分析・ラボで報告練習 | 2〜3時間 | 1件の事例分析と、自分の言葉で説明できる練習報告 |
| 正常動作の理解・仮説整理 | 1〜2時間 | 1機能のロール・データ境界と最大3仮説 |
| 許可された限定検証 | 1回60〜90分 | 1仮説につき確認・否定・未確認のいずれかを記録 |
| 候補の切り分け・最小再現・報告草案 | 2〜4時間を別枠で見込む | 候補がある場合のみ。独立した再現と影響を人が確認 |
| 初回応答・トリアージ・修正・支払 | 一律の時間を置かない | 選定先の表示する目標と実績を確認し、実作業とは別管理 |

目標応答時間は「提出後の処理目標」であって、こちらの発見所要時間ではない。[Response Target Metrics](https://docs.hackerone.com/en/articles/8505145-response-target-metrics)

公開成功談には、未発見に終わった時間、過去の経験、非公開の重複などが見えない。解説を見たCTFの速度から、未知の実対象を解く速度を外挿しない。「AIなら何倍速」といった根拠のない係数も置かない。

## 3. 2週間・12時間の試行案

週3回、各2時間。日程は任意で、予定登録や自動実行はしない。

1. **第1回: 候補とルール（2時間）** 公開VDPを最大3件比較し、条件に合う1件を仮選定。スコープと禁止事項を確認するだけで、まだ検査しない。
2. **第2回: 報告練習（2時間）** 関連する公開報告1件を読み、自分が理解しているCTF1件を報告形式に整理。実際に行った手順と解説由来の推測を分ける。
3. **第3回: 実行条件の確定と正常動作（2時間）** 利用者の承認、対象プログラムの許可、アカウント・データの扱いを確認後、1機能の正常動作を整理。条件が揃わなければラボで代替。
4. **第4回: 仮説1（2時間）** 最大90分の限定検証、残り30分で証跡と結果を整理。
5. **第5回: 仮説2または候補確認（2時間）** 前回と同じ探索の反復は避ける。候補があれば安全な最小再現を優先し、範囲を拡大しない。
6. **第6回: 評価・草案・次の判断（2時間）** 有効候補があれば草案。なければ除外できた仮説と学びをまとめ、継続・対象変更・学習への回帰を判断する。

12時間で報告が完成しなければ、未完成のまま区切る。追加2〜4時間を使うかは、候補の根拠を見て別途判断する。未発見でも、対象理解、検証記録、学習成果が残れば試行として成功。収益化を最初の合格条件にしない。

## 4. 対象選定の必須条件

次が全て確認できる対象だけを候補にする。

- 現在も有効なプログラムで、正確なドメイン・アプリ・APIと対象外が明示されている。
- 今回の検証方法が許され、参加条件、テスト用アカウント、データ作成条件が明確。
- 自分が管理するテストデータだけで検証可能。必要なら自分のテスト用2アカウント間で認可境界を比較できる。複数アカウント作成が許可されるかも確認する。
- 自動化、AI利用、通信量、同時実行、識別ヘッダー等の条件を確認できる。記載がないことを無制限許可と解釈しない。
- 報告先、対象外の脆弱性類型、公開条件、Safe Harborを確認できる。
- 課金、注文、実配送、他人への通知などの副作用を伴わずに調べられる。

まずWeb/APIの認可境界を候補にする。画面構成と自分のデータを理解しやすく、既存のCTF経験を活かしやすいためであり、発見しやすい保証ではない。旧ロードマップのWoltは候補名にすぎず、今回の対象として選定・検査していない。

Safe Harborは一般的な免責や全サービスの検査許可ではなく、採用プログラムの条件を読む必要がある。第三者インフラをその組織が代わりに許可できるわけではない。曖昧な範囲を推測で拡大しない。[公式Safe Harbor](https://docs.hackerone.com/en/articles/8494525-gold-standard-safe-harbor-statement)

## 5. AI / Computer Useの役割

Daybreak / Sol 5.0という呼称から、この環境の正式なモデルID、機能、速度を断定しない。ここでは、現在使用しているAIと画面操作機能を一般的な補助として設計する。特定モデルでのVDP実測値はない。

| AIに任せやすいこと | 人が確認すること |
| --- | --- |
| 公開規約の要約とチェックリスト作成 | 原文との照合、許可範囲、禁止事項 |
| 公開報告の整理、仮説を最大3件提案 | 仮説が対象の仕様に合うか |
| 承認済み操作の補助、記録整理 | 正しいホスト・アカウント・データか |
| 許可済みラボや自己所有コードの分析 | 出力の正しさ、実行の安全性 |
| 報告草案の整形、証跡の不足指摘 | 独立した再現、実際の影響、提出可否 |

高速化を期待するのは読み取り・整理・下書きであり、未知の脆弱性の存在そのものではない。画面操作はログインや表示差分、タイムアウトで余分な時間がかかる場合もある。入力されたページの指示を新たな許可と扱わず、別ホストへの遷移や送信先変更は止めて確認する。

HackerOneは責任あるAI補助を認める一方、利用者の検証責任、プログラムごとの自動化制限、人による確認を要求している。完全自律の大量探索・大量提出を運用目標にしない。[Code of Conduct](https://www.hackerone.com/policies/code-of-conduct)

外部AIへ送るのは公開資料または送信を明示的に許可された資料だけ。実対象の非公開レスポンス、認証値、個人情報を、公開情報の要約と同じ扱いにしない。ブラウザ画面の共有自体も情報送信になり得る。

### 効果を測る指標

各回に「人の実作業分」「AI待ち分」「接続・設定の復旧分」「検証済み仮説数」「人が訂正した誤り」「有効候補数」を記録する。AIの効果は文書作成等の同程度の作業で比較し、発見数だけで優劣を判断しない。無駄な再実行や実対象への比較用の重複検査はしない。

## 6. 初期運用の上限と停止ルール

以下はこの試行の保守的な提案であり、プログラムからの許可を代替しない。プログラムの条件がより厳しければそちらに従う。

- 対象は1プログラム・1機能、同時実行は1。広域スキャン、総当たり、パスワード試行、全件列挙、常駐探索は初期範囲外。
- 1仮説60分で中間判断、90分で打ち切り。1回2時間、合計12時間。新しい根拠なしに同じ試行を繰り返さない。
- 自動リクエストの初期予算は0。必要になったら、公式ルールと実行承認を確認し、数値のレート・総数・対象・時間を確定してから別計画にする。通常のページ読込みにも通信が発生するため、画面操作なら無制限としない。
- 429、サービス障害を示す5xx、アカウントロック、予期せぬ通知、データ変更、他者データへの接触があれば停止。大量再試行や制限回避をしない。
- スコープ不明、第三者ホストへの遷移、規約変更、予算切れ、保護機構の拒否、必要な権限不足で停止。別ブラウザ・別経路で拒否を回避しない。
- 影響を示すために必要以上のデータを取得しない。想定外の情報が見えたら、その時点の最小限の状況を安全に記録し、追加取得を止める。
- 課金、配送、契約、破壊的変更、第三者への連絡は初期範囲外。復旧を要する操作は事前に安全な復旧方法がない限り行わない。

停止後は「何が完了したか／何が未確認か／どの条件が揃えば再開できるか」を残す。許可された別のラボ学習や公開資料整理は続けられる。

## 7. 証跡と報告の運用

このリポジトリは公開されている。**実VDPの対象情報・未公開の発見・生のログ・Cookie・トークン・個人情報はここへ置かない。** 実対象の記録は公開Git作業ツリー外の、アクセスを制限した承認済み保管先へ置く。`.gitignore`だけを漏えい防止策としない。

公開repoに置くのは一般的な設計、空テンプレート、公開許可を確認した学習記録のみ。名前を伏せただけでも対象を推定できる情報は公開しない。公開済みレポートを参考にした場合も出典を示し、未確認の新規発見に見せない。

### 非公開セッション記録の空テンプレート

```markdown
# セッション記録
- 日時・実作業時間:
- 目標と終了条件:
- プログラムURL・規約確認日時:
- 許可範囲・禁止事項・自動化条件:
- ユーザー承認の対象・方法・上限:
- テストアカウントの役割（秘密の値は書かない）:
- 正常動作・期待結果:
- 仮説と根拠:
- 実施内容・実結果・必要最小限の証跡参照:
- 結果: 確認 / 否定 / 未確認
- 影響: 実証済み / 推測（区別する）
- 副作用・復旧確認:
- 次の1手、または停止理由:
```

### 提出前チェック

1. 現在のスコープ内か。既知事項・公開済み報告・対象外類型を確認したか。非公開の重複までは判断できないことを認識する。
2. 自分のテストデータだけで、別の人が追える最小限の再現手順があるか。
3. 正常な仕様や緩和策を考慮しても、実際のセキュリティ影響が残るか。
4. AIの推測や存在しないエンドポイントを事実として書いていないか。
5. 証跡を必要最小限にし、秘密・個人情報を除去したか。
6. 人が検証し、提出する内容と提出先を確認したか。草案作成だけでは自動提出しない。

### 報告草案の空テンプレート

```markdown
# [機能] の [問題] により [実証した影響]
## 概要
## 対象と前提条件
## 再現手順
1.
2.
3.
## 期待される結果
## 実際の結果
## 実証した影響と確認していない範囲
## 最小限の証跡
## 修正の提案（任意）
```

公式の品質ガイドも、明確な再現手順・期待と実結果・影響・必要な証跡を重視している。[Quality Reports](https://docs.hackerone.com/en/articles/8475116-quality-reports)

提出後は初回応答、トリアージ、修正、報奨を別の状態として記録する。提出済みを受理済みと数えない。公表は修正完了やDuplicate判定だけで判断せず、正式な開示手順と対象側の許可・公開範囲を確認してから行う。[Requesting Disclosure](https://docs.hackerone.com/en/articles/8475358-requesting-disclosure)

## 8. 12時間後の判断

| 状況 | 次の行動 |
| --- | --- |
| 再現・影響が確認できた候補あり | 残時間で草案、足りなければ追加枠を判断。送信は内容・宛先を確認後 |
| 正常動作は理解できたが候補なし | 根拠がある次の仮説がある場合だけ継続枠を設定 |
| 重複しやすい既知事項ばかり | 対象機能・仮説を変更。報告件数を作るために提出しない |
| 規約や対象範囲が曖昧 | 検査を止め、明確な候補に変更。必要な問い合わせは送信承認後 |
| 操作復旧に時間の大半を消費 | ラボ・自己所有コードのレビューへ切替え、Computer Use構成を別途見直す |
| 仕様理解・再現説明が不足 | 同じ類型のラボを1件だけ補強し、再挑戦を判断 |

「0件だった」を「安全である」とは結論しない。調べた範囲と限界を明記する。最初の一歩は第1回の候補比較であり、この設計を保存した時点では、実対象の検査、報告提出、支払、アカウント作成、定期実行は開始しない。
